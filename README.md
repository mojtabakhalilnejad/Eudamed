# EUDAMED Search (اندروید)

اپلیکیشن اندرویدی برای جستجوی دستگاه‌های پزشکی ثبت‌شده در پایگاه داده **EUDAMED** اتحادیه اروپا،
با فیلترهای ترکیبی (کمبوباکس با جستجوی مشابه/فازی) روی: اسم محصول، نام کمپانی سازنده، کشور سازنده،
کلاس ریسک، وضعیت دستگاه، نوع قانون (MDR/IVDR)، شماره UDI، تاریخ ثبت و تاریخ گرفتن CE.

فناوری: **Kotlin + Jetpack Compose (Material 3)**, Retrofit + OkHttp + kotlinx.serialization,
Navigation-Compose, min SDK 26 / target SDK 34.

---

## ⚠️ نکته‌ی خیلی مهم درباره‌ی API این پروژه

خود اتحادیه اروپا **دو** راه برای گرفتن داده از EUDAMED در اختیار می‌گذارد، و این پروژه هر دو را
پیاده‌سازی کرده (طبق انتخاب شما):

### ۱. «سایت EUDAMED» — پیش‌فرض، بدون کلید، داده‌ی زنده
اپ مستقیماً همان endpoint‌ی JSON را صدا می‌زند که خودِ وب‌سایت `ec.europa.eu/tools/eudamed`
هنگام جستجو استفاده می‌کند (مثل `GET /devices/udiDiData`). این کار نیاز به کلید ندارد و کامل‌ترین و
به‌روزترین داده را می‌دهد، **اما رسمی و مستندسازی‌شده توسط کمیسیون اروپا نیست** — یعنی هر لحظه ممکن
است بدون اطلاع قبلی تغییر کند. مستندات غیررسمی که این پیاده‌سازی بر اساس آن نوشته شده:
https://openregulatory.github.io/eudamed-api/

نکته‌ی فنی: فقط پارامترهای صفحه‌بندی (`page`, `pageSize`, `size`, `languageIso2Code`) در آن مستندات
تأیید شده‌اند. پارامترهای فیلتر (نام محصول، کمپانی، کلاس ریسک، ...) بر اساس رفتار مشاهده‌شده‌ی فرم
جستجوی خود سایت حدس زده شده‌اند (در `EudamedSiteApi.kt` و متد
`DeviceRepository.buildSiteParams`). اگر کمیسیون این پارامترها را عوض کند، فقط همین یک متد نیاز به
اصلاح دارد — بقیه‌ی اپ (UI، جستجوی فازی، دیتابیس مرجع) دست‌نخورده می‌ماند. به همین دلیل، برای
اطمینان از درستی نتیجه، اپ همیشه یک بار دیگر هم نتایج را **در خودِ گوشی** با تطبیق فازی فیلتر
می‌کند (بخش بعد را ببینید) — یعنی حتی اگر یک پارامتر توسط سرور نادیده گرفته شود، نتیجه‌ی نهایی که
کاربر می‌بیند همچنان درست فیلتر شده است.

### ۲. API رسمی EUDAMED Public v1.0 (DG SANTE)
یک API رسمی، مستند و پایدار که کمیسیون اروپا در پورتال زیر منتشر کرده:
https://developer.datalake.sante.service.ec.europa.eu/api-details#api=94b9e658-d721-4b58-8d96-022c490f7a17

برای استفاده باید در آن پورتال ثبت‌نام کنید و یک **Subscription Key** رایگان بگیرید (داخل اپ، از
آیکن تنظیمات در صفحه‌ی جستجو قابل وارد کردن است). این API:
- فقط جستجوی **دقیق (exact match)** می‌دهد، نه جستجوی جزئی/تقریبی سمت سرور،
- روی یک **snapshot شبانه** کار می‌کند، نه دیتابیس زنده،
- ساختار داقیق مسیر/پارامترهایش پشت لاگین آن پورتال است، بنابراین `EudamedOfficialApi.kt` بهترین
  حدس ممکن بر اساس نام‌گذاری استاندارد این نوع API‌هاست. با گرفتن دسترسی پورتال، کافیست مسیر و
  نام پارامترها در همین یک فایل اصلاح شود.

هر دو مسیر «Source: EUDAMED, European Commission» را باید در استفاده‌ی عمومی از داده ذکر کنند
(مجوز CC BY 4.0، تصمیم کمیسیون 2011/833/EU).

## جستجوی «مشابه» (fuzzy search) چطور کار می‌کند؟

چون هیچ‌کدام از دو API تضمین نمی‌کنند که جستجوی تایپ ناقص/غلط املایی را درست هندل کنند، تمام
منطق «پیدا کردن مشابه» **در خودِ اپ و آفلاین** پیاده‌سازی شده (`util/FuzzyMatcher.kt`):

- تطبیق دقیق / پیشوندی / شامل‌بودن → بالاترین امتیاز.
- تطبیق کلمه‌به‌کلمه (مثلاً «phil hue» با «Philips Hue Sensor» مچ می‌شود).
- فاصله‌ی ویرایشی Levenshtein برای غلط‌های تایپی («phillips» در برابر «philips»).

همین منطق در کمبوباکس‌ها (`ui/components/FuzzyComboBox.kt` و `RemoteFuzzyComboBox.kt`) استفاده
می‌شود تا هنگام تایپ، گزینه‌های نزدیک/مشابه پیشنهاد شوند، و دوباره روی نتایج برگشته از سرور اعمال
می‌شود تا نتیجه‌ی نهایی همیشه شامل موارد مشابه باشد، نه فقط تطبیق‌های ۱۰۰٪.

فیلدهای تاریخ (ثبت / CE) به‌جای یک تاریخ دقیق، به‌صورت «از – تا» طراحی شده‌اند
(`util/FuzzyDate.kt`) — چون خیلی از رکوردهای EUDAMED فقط تا سطح ماه/سال دقیق‌اند، بازه منطقی‌تر از
تطبیق روز-به-روز است.

## ساختار پروژه

```
app/src/main/java/com/openregulatory/eudamedsearch/
├── data/
│   ├── model/        مدل‌های داده + دیتای مرجع استاتیک (کشورها، کلاس ریسک، ...)
│   ├── remote/        Retrofit API interfaces + NetworkModule
│   └── repository/    DeviceRepository (منطق ترکیب سرور + فیلتر فازی) + SettingsStore
├── ui/
│   ├── components/     FuzzyComboBox, RemoteFuzzyComboBox, DateRangeField, DeviceListItem
│   ├── search/         صفحه‌ی جستجو + ViewModel + صفحه‌ی تنظیمات (کلید API)
│   ├── detail/         صفحه‌ی جزئیات دستگاه (شامل گواهی‌های CE)
│   └── theme/          تم Material 3 (روشن/تاریک، رنگ‌های اتحادیه اروپا)
├── nav/                گراف ناوبری Compose
├── MainActivity.kt
└── EudamedApp.kt
```

## راه‌اندازی در Android Studio

1. پروژه را در Android Studio (نسخه‌ی Koala 2024.1.1 یا جدیدتر) با **Open** باز کنید — همه‌ی
   فایل‌های Gradle Wrapper (`gradlew`, `gradlew.bat`, `gradle/wrapper/gradle-wrapper.jar`) از قبل
   داخل پروژه هستند و واقعی‌اند (نه دست‌نویس)، پس فقط کافیست پروژه Sync شود.
2. برای اجرا روی شبیه‌ساز/گوشی: دکمه Run را بزنید؛ چیز خاصی برای تنظیم لازم نیست چون منبع پیش‌فرض
   («سایت EUDAMED») بدون کلید کار می‌کند.
3. اگر می‌خواهید از API رسمی استفاده کنید: داخل اپ، سوییچ منبع داده را روی «API رسمی» بگذارید،
   Subscription Key خود را در صفحه‌ی تنظیمات وارد و ذخیره کنید.

## بیلد گرفتن با GitHub Actions

یک workflow آماده در `.github/workflows/build.yml` داخل پروژه هست. کافیست:

1. یک ریپازیتوری در GitHub بسازید و کل پوشه‌ی پروژه را push کنید (نیازی به هیچ تغییری نیست، حتی
   `gradlew` و wrapper از قبل واقعی و اجرایی‌اند).
2. به تب **Actions** ریپو بروید؛ روی هر push به شاخه‌ی `main`/`master` (یا اجرای دستی با
   «Run workflow»)، این workflow به‌صورت خودکار:
   - JDK 17 و Android SDK را نصب می‌کند،
   - `assembleDebug` و `assembleRelease` (بدون امضا) را می‌سازد،
   - تست‌های واحد را اجرا می‌کند،
   - APK های خروجی را به‌عنوان **Artifact** (پایین صفحه‌ی همان اجرای workflow) برای دانلود می‌گذارد.
3. APK دیباگ (`eudamed-search-debug`) مستقیماً روی گوشی نصب‌شدنی است (باید «نصب از منابع ناشناس»
   را برای فایلی که دانلود می‌کنید فعال کنید). APK ریلیز امضا نشده است — برای انتشار واقعی (مثلاً
   در Google Play) باید یک signing config و کلید امضا اضافه کنید؛ در آن صورت کلید امضا را به‌صورت
   GitHub Secret ذخیره کرده و مرحله‌ی امضا را به workflow اضافه کنید.

## محدودیت‌های شناخته‌شده

- endpoint سایت EUDAMED رسمی/تضمین‌شده نیست؛ در صورت تغییر ساختار توسط کمیسیون اروپا، فقط
  `EudamedSiteApi.kt` / `DeviceRepository.buildSiteParams` نیاز به به‌روزرسانی دارند.
- تاریخ CE دقیق هر گواهی فقط در صفحه‌ی جزئیات دستگاه (که یک درخواست جداگانه به API می‌زند) در
  دسترس است؛ فیلتر «تاریخ CE» در صفحه‌ی جستجو به‌صورت best-effort روی آخرین تاریخ به‌روزرسانی
  دستگاه اعمال می‌شود چون endpoint جستجو، تاریخ گواهی را برنمی‌گرداند.
- این پروژه هیچ داده‌ی شخصی افراد را ذخیره یا درخواست نمی‌کند؛ تنها داده‌ی محلی، کلید اختیاری API
  رسمی است که در SharedPreferences (و خارج از بک‌آپ) نگه‌داری می‌شود.
